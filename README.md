## Основное задание

### Решение

**Файл с реализацией `selectProducts`:**

[Решение](src/main/kotlin/lab2/ProductSelection.kt).

**Как работает функция и почему выбран такой способ обработки данных?**

По заданию **excludedIds** может содержать дубликаты, для избавления от них используется `Set`, также он позволяет делать проверку `!in excludedSet` за константное время O(1).
Для начала проходимся по списку продуктов и фильтруем его (товар доступен и не находится в **excludedIds**), после чего преобразуем отфильтрованный список в `Map`, где
в качестве ключа используется `id` продукта. Это сделано для дальнейшей возможности получить элемент за константное время O(1). Использование здесь `Sequence` не является уместным,
поскольку он не дает выйгрыша по времени выполнения и памяти, даже несмотря на создание промежуточного списка после функции `filter`. По заданию сказано, что **recommendedIds** также
может содержать дубликаты, для их устранения он также приводится к `Set`, после чего по нему совершается поэлементный обход, если товар с таким id присутствует в списке доступных продуктов,
то мы добавляем его в результат.

**Как сохраняются порядок рекомендаций и уникальность товаров? Как обрабатываются исключённые, недоступные и неизвестные товары?**

Порядок рекомендаций и уникальность товаров гарантируется преобразованием входных списков в `Set` с использованием функции `toSet()`, которая под капотом использует следующую структуру данных: `LinkedHashSet`.
Исключенный и недоступные товары фильтруются этой строчкой кода: `.filter { it.available && it.id !in excludedSet }`, а неизвестные товары отбрасываются здесь: 
`val currentProductOrNull = availableById[currentId]
if (currentProductOrNull != null) {}`.

### Сложность

Обозначения:

- `p` — число товаров в каталоге;
- `r` — число идентификаторов в рекомендациях;
- `e` — число идентификаторов в исключениях.

**Время выполнения:**

Преобразовать excludedIds в set: **O(e)** + преобразовать recommendedIds в set: **O(r)** + пройтись по этому set и выполнить константную операцию: **O(r)** + 
пройтись по списку продуктов, отфильтровать их и превратить в map: **O(2p)**. Суммарно получаем **O(e + 2r + 2p)**, что равняется **O(e + r + p)**. 
То есть линейной время, потому что в нотации **биг О** подразумевается асимптотическая сложность - константы отбрасываются. Стоит также учесть, что это оценка справедлива,
если:
+ операции с хеш-таблицами выполняются за O(1) в среднем
+ добавление в ArrayList стоит O(1) амортизированно

**Дополнительная память:**

+ excludedIds.toSet(): **O(e)** в худшем случае, если все id уникальны
+ промежуточный список после filter: **O(p)** в худшем случае, если все товары подходят
+ availableById (Map по id): **O(p)** в худшем случае, если все товары подходят
+ recommendedIds.toSet(): **O(r)** в худшем случае, если все id уникальны
+ result: **O(min(p, r))**

Итого дополнительная память (без result) равна **O(e) + O(p) + O(p) + O(r) = O(p + r + e)**. Константа 2 у p отбрасывается.

## Дополнительное задание

### Организация решения

- реализация: [ProductSelectionAdditional.kt](src/main/kotlin/lab2/ProductSelectionAdditional.kt)
- тесты: [ProductSelectionAdditionalTest.kt](src/test/kotlin/lab2/ProductSelectionAdditionalTest.kt)

```kotlin
val keyboard = Product(1, "Keyboard", true)
val mouse = Product(2, "Mouse", false)
val monitor = Product(3, "Monitor", true)
val webcam = Product(4, "Webcam", true)

val products = listOf(keyboard, webcam, mouse, monitor)

val catalog = Catalog(products) // каталог готовится один раз

val recommended = listOf(3L, 2L, 3L, 99L, 1L, 4L)

catalog.selectProducts(recommended, listOf(1L), 1) // [Monitor]
catalog.getCounter() // 1 (просмотрена одна рекомендация)

catalog.selectProducts(recommended, listOf(1L), 10) // [Monitor, Webcam]
catalog.getCounter() // 6 (просмотрены все рекомендации)

catalog.changeListOfProducts(newProducts) // загрузка нового каталога
```

**Что выполняется при загрузке каталога, а что — при каждом запросе? Как обеспечиваются независимость запросов и переход на новый каталог?**

При загрузке каталога (конструктор `Catalog` и метод `changeListOfProducts`) один раз выполняется работа, которая одинакова для всех запросов: из списка товаров оставляются только доступные `available = true`
и строится `Map` id - Product. При каждом запросе `selectProducts` делается только то, что зависит от самого запроса: из `excludedIds` строится множество исключений, создаются множество уже добавленных id
и список результата, затем просматриваются рекомендации. Каталог при этом не фильтруется и не перестраивается. Также счётчик просмотренных рекомендаций сбрасывается в начале каждого запроса,
в том числе при `limit = 0`. Объект рассчитан на последовательные вызовы, но стоит понимать, что он не потокобезопасен. Переход на новый каталог: `changeListOfProducts` полностью заменяет `Map`, поэтому следующие запросы
используют только новые данные, а товары старого каталога в результат не попадают.

**Когда прекращается просмотр рекомендаций? От чего зависит число просмотренных элементов?**

Просмотр идёт по `recommendedIds` по одному id, в исходном порядке. Он прекращается, когда размер результата достигает `limit`, либо когда рекомендации закончились. Рекомендации не преобразуются заранее (нет `toSet()` по всему списку),
повторы отсекаются по ходу через множество уже добавленных id. Поэтому после заполнения результата оставшиеся рекомендации не обрабатываются. При `limit = 0` просмотр не начинается, счётчик равен 0. Число просмотренных рекомендаций `v`
зависит от `limit` и от того, сколько «лишних» id встречается раньше. В лучшем случае `v = limit` (каждый просмотренный id подходит), в худшем `v = r` (подходящих товаров меньше лимита или они находятся в самом конце списка).

### Сложность

Обозначения:

- `p` — число товаров в каталоге;
- `r` — длина списка `recommendedIds` в запросе;
- `e` — длина списка `excludedIds` в запросе;
- `v` — число реально просмотренных рекомендаций, `v <= r`;
- `k` — размер результата, `k <= min(limit, p, v)`.

| Этап | Время | Дополнительная память |
|---|---|---|
| Подготовка каталога | O(p) | O(p) |
| Один запрос | O(e + v) | O(e + k) |

**Обоснование оценок и память для результата:**

Подготовка каталога: один проход по `p` товарам с фильтрацией по `available` и построением `Map` по id, то есть O(p) по времени. Промежуточный список после `filter` и сам `Map` занимают O(p) памяти.  Один запрос по времени: построение множества
исключений стоит O(e). Затем цикл просматривает `v` рекомендаций, и для каждой выполняет проверки по хеш-таблицам и добавление в список за O(1). Итого O(e + v). Размер каталога `p` в стоимость запроса не входит.  Один запрос по памяти: множество
исключений занимает O(e), множество уже добавленных id O(k). Память под результат учитывается отдельно: список результата занимает O(k), где `k ≤ min(limit, p)`. Входные списки и подготовленный `Map` в память запроса не входят. Условия, при которых
оценки справедливы: 
+ операции `HashSet`/`HashMap` выполняются за O(1) в среднем
+ добавление в `ArrayList` амортизированно O(1)
+ id в каталоге уникальны

| Что проверяется | Тесты                                                                                                                |

| Нулевой лимит | `returnsEmptyListForZeroLimit()`, `resetsCounterAfterZeroLimitRequest()`                                               |

| Подходящих товаров меньше лимита | `returnsAllFoundWhenLimitIsBigger()`                                                                                   |
| Несколько независимых запросов к одному каталогу | `queriesToSameCatalogDoNotAffectEachOther()`, `counterIsResetForEachRequest()`                                           |
| Переход на новый каталог | `usesNewDataAfterChangingCatalog()`, `oldCatalogProductsAreNotReturnedAfterChange()`                                     |

**Как подтверждено досрочное завершение?**

Тест `stopsViewingWhenResultIsFull`: каталог из четырёх товаров, рекомендации `[3, 4]` и после них 100 000 раз 99 (неизвестный id), всего 100 002 рекомендации, `limit = 2`. Ожидаемый результат `[Monitor, Webcam]`, число просмотренных рекомендаций равно 2, то есть оставшиеся 100 000 не просматривались.
Тест `countsDuplicatesAndUnknownIdsBeforeFullResult`: рекомендации `[3, 3, 99, 2, 4, 1, 1]` (всего 7), `limit = 2`. Результат `[Monitor, Webcam]`, просмотрено 5, последние два id не просматривались. Это показывает, что счётчик учитывает повторы, неизвестные и недоступные id.
Способ подсчёта: в начале каждого запроса поле счётчика обнуляется, затем в цикле по рекомендациям счётчик увеличивается на 1 на каждом просмотренном id (до проверки на повтор и до остальных проверок). Значение читается через `getCounter()`. Счётчик не влияет на возвращаемый список.
